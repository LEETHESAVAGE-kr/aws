## 1. README 9절 구성 (FR-11 고정 순서)

README.md는 반드시 아래 9개 절을 이 순서로 포함한다. 절 순서 변경·생략 금지.

| 절 번호 | 제목 (고정) | 주요 내용 |
|---------|------------|-----------|
| § 1 | 문제 | 60초 HAZOP 설명 + 실제 사고 사례 1건 (NH3 또는 유사 화학물질 사고) |
| § 2 | 왜 LLM인가 | 기존 수작업 HAZOP의 한계 + LLM 접근의 차별점 |
| § 3 | 데이터 · 라이선스 | 사용 데이터 목록, 출처, 라이선스. `data/README.md` 링크 포함 |
| § 4 | 아키텍처 | 시스템 다이어그램 (텍스트 또는 이미지), 컴포넌트 설명 |
| § 5 | Kiro 개발 방식 · 추적 매트릭스 | Kiro spec 활용 방식 설명 + §2 추적 매트릭스 표 |
| § 6 | 평가 결과 | 평가 지표 표 (불리한 지표 포함 필수 — §3 규칙 참조) |

| § 8 | 실행 방법 | 새 머신에서 5분 내 실행 완료 기준으로 작성. `make setup && make demo` |
| § 9 | 비용 | 노드 1건 비용 실측값, 총 개발 비용, 대회 크레딧 잔량 기록 |

절 제목은 한글로 작성한다. 영문 병기 가능 (예: `## § 6 평가 결과 (Evaluation Results)`).

## 2. 추적 매트릭스 규칙

README § 5의 추적 매트릭스는 아래 4열 형식을 따른다.

### 형식

```markdown
| 요구사항 ID | 코드 모듈 | 테스트 ID | 측정 지표 |
|------------|----------|----------|----------|
| R-xx (requirements.md) | 모듈 경로 | T-xx (tasks.md) | 지표명 = 목표값 |
```

### 예시

| 요구사항 ID | 코드 모듈 | 테스트 ID | 측정 지표 |
|------------|----------|----------|----------|
| R-03 이탈 생성 | `core/agent/generate.py` | T-07 | recall ≥ 0.70 (홀드아웃) |
| R-04 근거 인용 | `core/agent/tools/kb_search.py` | T-12 | 근거 첨부율 ≥ 80% |
| R-06 자기 검증 | `core/agent/verify.py` | T-15 | 플래그 정확도 ≥ 90% |
| R-08 평가 하네스 | `eval/run.py` | T-20 | 5회 반복 평균±표준편차 표 |

### 규칙

- `R-xx`는 해당 spec의 `requirements.md` requirement ID와 일치해야 한다.
- `T-xx`는 해당 spec의 `tasks.md` task ID와 일치해야 한다.
- 지표가 없는 요구사항(순수 구조·인프라)도 "지표: 통합 테스트 통과"로 기재.
- spec이 완성될 때마다 매트릭스를 갱신한다 (훅 `spec-to-readme`가 자동 생성 보조).

## 3. 평가 결과 표 규칙 (NFR-03 신뢰성 공개)

README § 6의 평가 표는 다음 규칙을 따른다.

### 필수 포함 지표

| 지표 | 단위 | 비고 |
|------|------|------|
| 이탈 recall | 0~1 | 홀드아웃 노드 기준 |
| 이탈 precision | 0~1 | |
| S 등급 MAE | 등급 | |
| F 등급 MAE | 등급 | |
| 근거 첨부율 | % | 이탈 중 evidence[] 비어있지 않은 비율 |
| 근거 정확도 | 0~1 | 수작업 채점 30건 기준 |
| 환각률 | % | verifier `review` 비율 + 수작업 확인 |
| 노드당 지연 | 초 (P90) | |
| 노드당 토큰 | tokens | 입력+출력 합산 |
| 노드당 비용 | USD | 평균 |

### 불리한 지표 포함 원칙

- **불리한 지표(낮은 recall, 높은 환각률 등)는 제거하거나 축소 표기하지 않는다.**
- recall이 목표(0.70) 미달이면 현재 달성값을 표에 그대로 표기하고 § 7 한계에서 원인 서술.
- 5회 반복 평균±표준편차 형식으로 기재: `0.68 ± 0.04`.
- 수작업 채점 방법론(채점자·기준·건수)을 표 아래 주석으로 명시.

### 표 형식 예시

```markdown
| 지표 | 값 (평균 ± 표준편차) | 목표 | 달성 여부 |
|------|---------------------|------|----------|
| 이탈 recall | 0.68 ± 0.04 | ≥ 0.70 | ⚠️ 미달 |
| 근거 첨부율 | 83% ± 2% | ≥ 80% | ✅ 달성 |
| 환각률 | 12% ± 3% | 공개 | — |
| 노드당 비용 | $0.18 ± 0.03 | ≤ $0.30 | ✅ 달성 |

> 수작업 채점: 홀드아웃 노드 이탈 30건을 안전공학 지식을 보유한 1인이 채점.
> 채점 기준: 인용 문단이 주장하는 원인/결과를 직접 지지하면 정확, 간접 참고는 부분 점수.
```

## 4. data/README.md 출처·라이선스 표 형식

`data/README.md`에는 모든 데이터 자산의 출처와 라이선스를 아래 표로 기재한다.
README.md § 3에서 이 파일로 링크.

### 형식

```markdown
## 데이터 자산 출처·라이선스

| 파일 / 경로 | 설명 | 출처 | 라이선스 | 취득일 |
|------------|------|------|---------|--------|
| `data/gold/hazop_nh3.json` | NH3 HAZOP 골드셋 | 팀 보유 경진대회 데이터 | 비공개 (제출용, 외부 배포 금지) | 2026-09 |
| `data/kb/kosha/P-xxx.pdf` | KOSHA Guide P-xxx | KOSHA 공식 홈페이지 | 공공누리 1유형 | 2026-09 |
| `data/kb/substances.json` | 화학물질 속성 캐시 | KOSHA 화학물질정보 | 공공누리 1유형 | 2026-09 |
| `data/kb/registers.json` | 고장률·가정 대장 | NH3 QRA 문헌대장 (팀 보유) | 비공개 | 2026-09 |
```

### 규칙

- **KECC 고객사 실데이터는 절대 포함 금지.** 포함된 경우 즉시 제거하고 커밋 이력에서 squash.
- 라이선스 불명확 데이터는 사용 금지. 불명확 시 팀 내 확인 후 기재.
- 공공누리 1유형: 출처 표시 후 자유 이용 가능. 표에 원본 URL 포함 권장.
- 각 PDF/JSON 파일 옆에 `.meta.json` (code, title, revision_year, source_url) 생성 권장.

## 5. spec 문서 작성 규칙

`.kiro/specs/<spec>/` 내 `requirements.md`, `design.md`, `tasks.md` 작성 시:

### requirements.md
- EARS(Easy Approach to Requirements Syntax) 형식 사용.
- 각 requirement에 수용 기준(Acceptance Criteria) 포함.
- ID 형식: `R-xx` (두 자리 숫자, 01부터).

### design.md
- 아키텍처 결정 근거 포함 (왜 이 방식을 선택했는가).
- 데이터 흐름 다이어그램은 Mermaid 또는 ASCII art.

### tasks.md
- ID 형식: `T-xx` (두 자리 숫자, 01부터).
- 각 태스크에 완료 조건(Definition of Done) 명시.
- 커밋 메시지와 T-xx 번호 일치.
