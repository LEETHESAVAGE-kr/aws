# 사전등록 — 생성 방식 '3번 생성해 합치기'(합집합) 골드셋 대조 (2026-10-11)

측정 전에 커밋한다. 이 문서의 규칙은 결과를 본 뒤 바꾸지 않는다. 도구: `tools/measure_union.py`.

## 1. 무엇을 재나
화면 '3번 생성해 합치기'(10/10, `consensus_union=True`)가 골드 원인을 한 번 생성보다 더 많이 담는가.
합치기의 목적은 "한 번 생성에서 빠질 수 있는 원인까지 모은다"이므로 1차 지표는 **원인 단위 recall** 이다.

## 2. 조건
- 노드: N1(튜닝 노드) · N2·N3·N4(홀드아웃). 골드 레코드 34건, 레코드당 원인 1개.
- 모델: 대회 게이트웨이(`HAZOP_PROVIDER=gateway`) 생성 `bedrock-claude-opus-4-8`, 판정자 `bedrock-haiku`.
- 설정: `config/models.yaml` 그대로(evidence_k 2 · inference_boundary true · parallel 7) + `consensus_runs=3`. 기준 `GOLD_CRITERIA`.
- 노드마다 판정 3번 **한 벌**. 같은 원자료에서 다섯 방식을 만든다: 한 번 생성 #1·#2·#3, 공통 답(교집합), 합치기(합집합).
  파라미터 열거는 1회 공유 — 열거에서 빠진 파라미터는 어느 방식으로도 못 찾는다(알려진 천장).

## 3. 지표
1. **원인 recall(1차)** = 골드 원인 중 "같은 칸(가이드워드 정확 일치 + 파라미터 정규화 일치)의 원인 칸에 같은 사고 원인을 가리키는 문장이 있는" 건수 / 34.
   - 판정자: 골드 원인 1건마다 haiku 1회. 입력 = 골드 이탈·원인, 후보 = 그 칸에서 세 실행이 낸 원인 문장 전부(중복 제거, 번호).
     출력 = 같은 사고 원인(같은 기기·같은 고장·오조작 방식)을 가리키는 후보 번호 목록. 판정자는 문장이 어느 방식에서 왔는지 모른다.
   - 방식별 적중 = 그 방식의 원인 칸에 판정자가 고른 문장이 그대로(문자열 일치) 있는가. 합치기 칸은 묶음 대표 문장만 남으므로,
     같은 묶음의 다른 문장만 맞았으면 합치기는 적중이 아니다.
2. 칸 recall = 기존 `recall_for_node` (가이드워드×파라미터).
3. 검토 부담 = 해당 행 수 · 원인 문장 수(방식별).

## 4. 쓸 수 있는 말 (결과 보기 전에 정함)
- 비교는 "합치기" 대 "한 번 생성 #1~#3 평균"과 "최솟값~최댓값", 그리고 "공통 답". 건수 그대로 적는다(n=34, 검정 없음).
- 합치기 > 한 번 생성 평균이면: "이 측정(노드 4개·생성 한 벌·판정자 haiku)에서 골드 원인 a/34 대 평균 b/34".
- 같거나 낮으면 그대로 적는다. "더 정확하다"는 어느 경우에도 쓰지 않는다 — 정밀도(틀린 원인 비율)는 골드가 전수가 아니라 재지 않는다.
- 판정자 오류가 있을 수 있다 — 판정 원문(후보·선택 번호)을 결과 파일에 남겨 사람이 다시 볼 수 있게 한다.
