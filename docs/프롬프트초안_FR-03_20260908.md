# 프롬프트 초안 — FR-03 이탈 생성 루프 (매트릭스 선열거) · 2026-09-08

## 0. 이 문서의 지위

- `.kiro/specs/hazop-generation/` 이 **아직 없다**. 이 문서는 spec 이 나올 때까지 코드를 쓰지 않고
  진행할 수 있는 설계 초안이며, **코드가 아니다**(CLAUDE.md 정본 사슬 · PRD §7 NFR-01).
- spec 생성 후 §4 프롬프트 본문은 `core/agent/prompts/*.md` 로, §5 스키마는
  `schemas/deviation.schema.json` 으로 그대로 옮길 수 있게 작성했다.
- §7 은 **Kiro requirements.md 에 반영이 필요한 제안**이다. 이 세션이 직접 고치지 않는다.
- 튜닝 근거는 `data/gold/hazop_nh3_tune.json`(N1 8건)으로 한정한다
  (`split_config.json`: `tune_nodes=["N1"]`). 홀드아웃 N2·N3·N4 26건의 내용을 프롬프트에
  넣지 않는다 — §2 의 홀드아웃 통계는 **설계 위험 진단 목적으로만** 읽고, 어휘·표현을
  프롬프트로 옮기지 않았다.

## 1. 결론 먼저

지시문 C 가 요구하는 "가이드워드 7종 × 파라미터를 먼저 열거" 를 **표준 어휘 고정 목록**으로
구현하면, 골드셋 매칭이 (가이드워드, 파라미터) 문자열 기준일 때 **홀드아웃 recall 상한이
0.192** 다. PRD FR-03 의 최종 목표 0.7 은 물론이고 재판정 기준선도 넘지 못한다.

원인은 모델 성능이 아니라 **골드셋 파라미터 어휘가 표준 12종 목록과 거의 겹치지 않는다**는
데이터 사실이다(§2). 따라서 파라미터 축을 **고정 목록이 아니라 노드 메타에서 도출**하는
2단 매트릭스로 설계했다(§3).

G1(9/10) 킬체크는 N1 8건 기준이고 N1 상한은 0.875 라 기준 0.5 자체는 위태롭지 않다.
**위험은 G1 이 아니라 그 뒤 홀드아웃에서 드러난다** — N1 만 보면 이 함정이 보이지 않는다.

## 2. 실측 — 골드셋 어휘 분포 (2026-09-08, `data/gold/hazop_nh3.json` 34건)

### 2.1 가이드워드 분포

| 가이드워드 | 건수 | 표준 7종 여부 |
|---|---:|---|
| More | 9 | ✅ |
| No | 5 | ✅ |
| Other than | 5 | ✅ |
| Less | 4 | ✅ |
| Reverse | 2 | ✅ |
| **Too early** | 3 | ❌ 절차형 |
| **Too late** | 3 | ❌ 절차형 |
| **Wrong action** | 3 | ❌ 절차형 |

- `Part of` · `As well as` 는 골드셋에 **0건**이다. 열거는 하되 적용 판정에서 대부분
  "미적용" 으로 떨어질 것을 예상해야 한다(precision 하락 요인).
- 절차형 9건은 전부 N4(이송 운전 절차) 노드다 — 지시문 C §3 주의사항과 일치.

### 2.2 파라미터 분포 — **핵심 발견**

`.kiro/steering/domain.md` §2 표준 파라미터(유량·압력·온도·조성/농도·준위/액위·점도·반응·
상·시간·기동정지·유틸리티·유지보수) 대비:

| 표준 목록 안 | 건수 | 표준 목록 밖 | 건수 |
|---|---:|---|---:|
| 유량 | 4 | 계측, 장력, 곡률반경, 재질, 외부 충격, 운동 반복, 지지, 마모, 밀봉, 예냉, 개스킷 사양, 본딩, 개시, ESD, 밸브 순서, 분리, 퍼징 생략, 기상 중단, 통신, 접근 허용, 대피 방송, 수분사 | 각 1 |
| 압력 | 3 | | |
| 온도 | 3 | | |
| 조성 | 1 | | |
| 액위 | 1 | | |
| **소계** | **12 (35.3%)** | **소계** | **22 (64.7%)** |

### 2.3 표준 어휘만 열거했을 때의 구조적 recall 상한

가이드워드·파라미터가 **둘 다** 표준 목록 안에 있는 레코드만 도달 가능하다고 볼 때:

| 노드 | 건수 | GW 표준 | 파라미터 표준 | 둘 다 | **상한** |
|---|---:|---:|---:|---:|---:|
| N1 (튜닝, 매니폴드) | 8 | 8 | 7 | 7 | **0.875** |
| N2 (이송 호스) | 9 | 9 | 2 | 2 | **0.222** |
| N3 (수급선 매니폴드) | 7 | 7 | 3 | 3 | **0.429** |
| N4 (운전 절차) | 10 | 1 | 0 | 0 | **0.000** |
| 전체 | 34 | 25 | 12 | 12 | 0.353 |
| **홀드아웃(N2·N3·N4)** | 26 | 17 | 5 | 5 | **0.192** |

N1 에서 유일하게 표준 밖인 것은 `nh3-008 Other than / 계측`(가스감지 기능 상실) 1건이다.
**튜닝셋만 보면 파라미터 어휘 문제가 1/8 로만 보이지만, 홀드아웃에서는 21/26 이다.**

### 2.4 노드 메타가 비어 있다

골드셋 34건 전부 `phase="unknown"`, `P_kPag=null`, `T_degC=null`, `safeguards=[]` 이고
`equipment` 는 문자열 1개다(예: `["벙커링선 매니폴드"]`). 프롬프트가 받을 수 있는 실질
정보는 **물질명(NH3) + 설비명 1개**뿐이다.

- 함의 ①: 매트릭스의 파라미터 축은 사실상 `equipment` 문자열 하나에서 도출해야 한다.
- 함의 ②: 운전조건(P·T)에 근거한 S 등급 산정은 이 골드셋에서 불가능하다. S·F 는 물질
  독성과 설비 유형에 기반한 정성 판단이 된다 — 평가 시 MAE 가 나쁘게 나올 근거를 미리 적어 둔다.
- 함의 ③: 데모 프리셋(FR-10)에서는 P·T 를 채운 노드를 쓸 수 있으나, **골드셋 평가와
  데모는 입력 충실도가 다르다**는 점을 README 평가표 각주에 써야 한다(NFR-03).

## 3. 매트릭스 설계안

### 3.1 왜 고정 목록이 아닌가

§2.3 이 근거다. 추가로, 고정 목록을 골드셋 어휘로 채우는 것(장력·곡률반경·밀봉 …)은
**홀드아웃 누출**이라 금지한다. N2~N4 를 보고 만든 어휘를 프롬프트에 박으면 그 뒤의
recall 숫자는 아무것도 증명하지 못한다.

정직하게 상한을 올리는 방법은 하나뿐이다 — **모델이 노드 메타에서 파라미터를 스스로 도출**하게
하고, 그 도출 능력을 평가 대상에 포함시키는 것.

### 3.2 2단 매트릭스

```
[호출 1] 매트릭스 열거 (matrix_enumerate)
  입력: node_meta (물질·상·P·T·설비·기존 안전장치)
  출력: parameters[]  — 이 노드에 적용 가능한 파라미터 축
        · 표준 12종 중 해당하는 것 (domain.md §2)
        · + 설비 고유 축 (설비의 기능·재질·연결·계장·구조 완결성에서 도출)
        각 파라미터에 도출 근거 1줄
  ↓
[호출 2..n] 셀 판정·이탈 생성 (deviation_generate) — 가이드워드 단위 배치
  입력: node_meta + parameters[] + rating_scale + 담당 가이드워드 1종
  출력: 그 가이드워드 행의 전 셀에 대해 {applicable: true|false, 이탈 레코드 | 미적용 사유}
  ↓
[코드] risk_score = S × F  (모델에게 곱셈을 시키지 않는다 — 지시문 C §4)
       셀 커버리지 검증: 열거된 셀 수 == 판정된 셀 수. 불일치 시 WARNING + 재요청 없이 기록
```

- 가이드워드 축은 **고정**(표준 7종). 데이터가 축을 정의하는 게 아니라 방법론이 정의한다.
- 파라미터 축만 **도출**. 이게 §2.2 의 64.7% 를 겨냥한다.
- 호출을 가이드워드 단위로 쪼개는 이유: 파라미터 8개 × 7 = 56 셀을 한 번에 판정시키면
  뒤쪽 셀의 판정 품질이 떨어지고 `max_tokens: 4096` 을 넘긴다. 행 단위면 8셀/호출이다.

### 3.3 절차형 가이드워드 처리 — **requirements 결정 필요 사항**

지시문 C §3 이 "명시적으로 결정하라" 고 한 항목이다. 이 문서의 권고는 **조건부 포함**이다.

- 노드 메타의 `equipment` 가 절차·운전을 가리킬 때만(예: "이송 운전 절차") 가이드워드 축을
  표준 7종 + `Too early` · `Too late` · `Wrong action` 3종으로 확장한다.
- 근거: 이 3종은 IEC 61882 계열에서 배치·절차 노드에 쓰는 확장 가이드워드다. 골드셋에서
  9건 전부 N4 절차 노드에 몰려 있다는 사실과 일치한다.
- 포함하지 않을 경우의 대가는 §2.3 의 N4 행 — **N4 recall 상한 0.000**, 홀드아웃 전체
  상한 0.192. 포함할 경우 N4 상한은 가이드워드 축에서는 풀리지만 파라미터 축(§2.2)이
  여전히 0/10 이므로, **파라미터 도출(§3.2)과 매칭 규칙 완화(§7-②)가 같이 가야 의미가 있다.**
- 어느 쪽으로 결정하든 수용 기준에 상한 숫자를 적는다(NFR-03).

## 4. 프롬프트 초안

spec 확정 후 아래 두 블록을 `core/agent/prompts/matrix_enumerate.md` ·
`core/agent/prompts/deviation_generate.md` 로 옮긴다. 캐싱 경계는 §6.

### 4.1 `matrix_enumerate.md` (시스템)

```markdown
당신은 화공 공정 HAZOP 검토를 진행하는 위험성평가 전문가다.
주어진 공정 노드 하나에 대해, HAZOP 매트릭스의 **파라미터 축**을 결정하는 것이 이번 임무다.
이탈 시나리오는 아직 쓰지 않는다.

## 절차
1. 노드의 설계 의도를 한 문장으로 재구성한다(무엇이 어디서 어디로, 어떤 조건에서).
2. 그 설계 의도가 깨질 수 있는 **관점(파라미터)** 을 열거한다.
   - 먼저 표준 공정 파라미터 중 이 노드에 실재하는 것만 고른다:
     유량 · 압력 · 온도 · 조성 · 준위 · 점도 · 반응 · 상 · 시간 · 기동정지 · 유틸리티 · 유지보수
   - 그다음 이 설비 고유의 파라미터를 추가한다. 설비의 물리적 완결성·연결부·계장·
     구조 지지·운전 절차 관점에서, 위 표준 목록이 담지 못하는 축이 있으면 그것을 만든다.
     (예시가 아니라 원칙: "이 설비가 제 기능을 잃는 방식"이 표준 12종으로 다 표현되면
      추가하지 않고, 표현되지 않으면 그 방식을 파라미터 이름으로 만든다.)
3. 각 파라미터에 왜 이 노드에 적용되는지 한 줄 근거를 붙인다.

## 제약
- 파라미터는 6개 이상 12개 이하.
- 파라미터 이름은 한국어 명사구 4어절 이내.
- 노드 메타에 없는 설비·물질을 지어내지 않는다. 주어진 것만으로 판단한다.
- 정보가 부족해 판단할 수 없으면 그 파라미터를 넣지 말고, 부족하다고 적지도 마라 —
  열거에서 빼는 것으로 표현한다.
```

사용자 턴:

```markdown
## 노드
{node_id}

## 노드 메타
- 물질: {substance}
- 상(phase): {phase}
- 운전압력: {P_kPag} kPag
- 운전온도: {T_degC} °C
- 설비: {equipment}
- 기존 안전장치: {safeguards}

값이 unknown 또는 null 인 항목은 "미상"으로 취급하고, 미상을 이유로 파라미터를
제외하지는 마라(설비 유형만으로 판단 가능한 축은 남긴다).
```

### 4.2 `deviation_generate.md` (시스템)

```markdown
당신은 화공 공정 HAZOP 검토를 진행하는 위험성평가 전문가다.
가이드워드 1종에 대해, 주어진 파라미터 전부와의 조합(매트릭스 한 행)을 **빠짐없이** 판정한다.

## 절차 — 파라미터마다 반드시 이 순서로
1. 이 가이드워드를 이 파라미터에 적용했을 때 물리적으로 성립하는 이탈이 있는가?
   - 없으면 applicable=false 와 사유 한 줄. **셀을 건너뛰지 마라.**
2. 성립하면 이탈을 기술한다:
   - deviation: 이 노드에서 실제로 관측되는 상태로 기술한다(가이드워드 낱말의 반복 금지).
   - causes: 이 노드의 설비·운전에서 나오는 구체적 원인.
   - consequences: 물질의 위험성과 설비 손상 경로를 잇는다.
   - safeguards_before: **노드 메타에 주어진 기존 안전장치 중에서만** 고른다.
     주어지지 않았으면 빈 배열로 둔다. 있을 법한 안전장치를 지어내지 마라.
   - recommendations: 기존 안전장치의 공백을 메우는 조치.
3. S·F 를 아래 등급표에 따라 정수 1~5 로 매긴다. 위험도(S×F)는 계산하지 마라 —
   시스템이 계산한다.

## S·F 등급표
{rating_scale}

## 금지
- 규격 번호·기술지침 코드·문헌 수치를 인용하지 마라. 이 단계에는 근거 검색 도구가 없다.
  근거 인용은 다음 단계(FR-04)에서 붙는다.
- 노드 메타에 없는 설비·계장·물질을 새로 만들지 마라.
- 한 셀에 이탈을 2개 이상 넣지 마라. 서로 다른 이탈이면 서로 다른 셀로 가야 한다.
```

사용자 턴:

```markdown
## 노드
{node_id} · {substance} · {equipment}

## 이번 가이드워드
{guideword} — {guideword_definition}

## 판정할 파라미터 ({n}개, 전부 판정할 것)
{parameters_with_rationale}
```

### 4.3 프롬프트 설계 판단 3가지 (근거)

| 판단 | 이유 |
|---|---|
| 파라미터 예시를 프롬프트에 나열하지 않음 | §3.1 누출 방지. "원칙만 주고 예시는 주지 않는다" 를 §4.1 절차 2 에 명시했다 |
| `applicable=false` 셀도 반환하게 함 | 누락 방지가 매트릭스 선열거의 목적(지시문 C §3). 열거 셀 수 ↔ 판정 셀 수 대조로 누락을 코드가 검증할 수 있다 |
| `safeguards_before` 를 메타에 있는 것으로 한정 | 골드셋은 `safeguards=[]` 인데 골드 레코드의 `safeguards_before` 에는 값이 있다(예: "압력계 감시"). 모델이 이 칸을 채우려 들면 환각이 된다. 빈 배열을 허용해 FR-06 verifier 가 판단하게 남긴다 |

## 5. 출력 스키마 초안 (`schemas/deviation.schema.json`)

`gold_record.schema.json` + `evidence[]` + `confidence`. 이 spec 에서 `evidence` 는 항상
빈 배열, `confidence` 는 `"inferred"` 고정이다(지시문 C §2).

**주의 — 최상위는 객체여야 한다.** `core/llm/client.py` 는 `response_schema` 를
`structured_output` tool 의 `inputSchema` 로 넣는다(`build_structured_output_tool`).
Bedrock toolSpec 의 inputSchema 는 객체 스키마라 배열을 최상위로 둘 수 없다.

```jsonc
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "DeviationBatch",
  "type": "object",
  "required": ["guideword", "cells"],
  "properties": {
    "guideword": { "type": "string" },
    "cells": {
      "type": "array",
      "items": {
        "type": "object",
        "required": ["parameter", "applicable"],
        "properties": {
          "parameter":  { "type": "string", "minLength": 1 },
          "applicable": { "type": "boolean" },
          "skip_reason":{ "type": "string" },           // applicable=false 일 때
          "deviation":  { "type": "string" },
          "causes":            { "type": "array", "items": { "type": "string" } },
          "consequences":      { "type": "array", "items": { "type": "string" } },
          "safeguards_before": { "type": "array", "items": { "type": "string" } },
          "S": { "type": "integer", "minimum": 1, "maximum": 5 },
          "F": { "type": "integer", "minimum": 1, "maximum": 5 },
          "recommendations":   { "type": "array", "items": { "type": "string" } },
          "evidence":   { "type": "array", "items": {}, "maxItems": 0 },
          "confidence": { "type": "string", "enum": ["inferred"] }
        },
        "additionalProperties": false
      }
    }
  },
  "additionalProperties": false
}
```

- `risk_score` 는 스키마에 넣지 않는다 — 코드가 계산한다(지시문 C §4).
- `id` · `node` · `node_meta` · `scenario` 도 모델이 채우지 않는다. 코드가 조립한다.
  (`scenario` 는 QRA 시나리오 ID 라 이 spec 범위 밖이다. 빈 문자열로 둔다.)
- 검증 실패 시 동작은 `core/llm` 의 기존 규칙을 그대로 쓴다 — 1회 재시도 후
  `content=None` + `confidence_override="review"`. **`content` 가 `None` 으로 돌아오는
  경로가 있으므로 `generate.py` 는 이를 반드시 처리해야 한다**(그 가이드워드 행 전체를
  `review` 로 기록하고 빈 셀로 남긴다. 예외를 던져 노드 전체를 죽이지 않는다).

## 6. 호출 구조 · 캐싱 · 비용

| 항목 | 값 |
|---|---|
| 노드당 호출 수 | 1(열거) + 7~10(가이드워드 행) = **8~11회** |
| 캐싱 경계 | `deviation_generate` 시스템 프롬프트 + S·F 등급표. 노드 1건 안에서 7~10회 반복되므로 캐시 적중 대상이 명확하다(steering aws.md §4) |
| 캐싱 비대상 | `matrix_enumerate` — 노드당 1회뿐이라 캐시 이득이 없다 |
| 비용 상한 | 노드 1건 USD 0.30 (`cost_limit_usd`). `AbstractBedrockClient._check_cost_limit` 는 **호출 1건씩** 검사하므로, 노드 누적 비용 검사는 `generate.py` 가 별도로 해야 한다 |
| 지연 | NFR-06 60초. 가이드워드 행을 순차 호출하면 초과 위험 → 병렬화 여부는 실측 후 결정 |

**실측 없이 숫자를 쓰지 않는다.** 토큰·비용·지연은 전부 **미측정**이다
(`config/models.yaml` 의 `generation.model_id` 가 `null`, G0 미완료).

## 7. Kiro requirements.md 에 반영 제안

이 세션은 `.kiro/specs/*/requirements.md` 를 고치지 않는다(CLAUDE.md). 아래는 제안이다.

① **파라미터 축은 고정 목록이 아니라 노드 메타에서 도출한다**를 요구사항으로 명시.
   수용 기준에 §2.3 상한표를 근거로 "표준 12종 고정 시 홀드아웃 recall 상한 0.192" 를 적는다.

② **FR-08(evaluation-harness) 매칭 규칙 — 이 spec 밖이지만 지금 결정해야 한다.**
   PRD §5 FR-08 은 "(가이드워드, 파라미터) 정확 일치 + 이탈 텍스트 의미 유사도" 다.
   파라미터에 정확 일치를 요구하면 §2.3 상한이 그대로 천장이 된다. 제안:
   **가이드워드는 정확 일치, 파라미터는 정규화 + 의미 유사도**로 낮추고 그 사실과 임계값을
   README 에 명시(NFR-03). 이 변경 없이는 파라미터 도출 설계의 효과가 지표에 나타나지 않는다.

③ **절차형 가이드워드 3종은 조건부 포함**(§3.3). 포함/미포함 어느 쪽이든 상한 숫자를
   수용 기준에 적는다.

④ **`content=None` 경로 처리**를 수용 기준에 넣는다(§5 마지막 문단).

⑤ `Part of` · `As well as` 는 골드셋 0건이다. 열거는 유지하되 **precision 지표에서
   이 두 행의 기여를 별도 표기**하도록 FR-08 에 요청.

## 8. 오프라인 테스트 설계 (spec 승인 후 `tests/test_generate.py`)

`MockBedrockClient(responses=[...])` 또는 `response_factory` 로 자격증명 없이 전 흐름을 돈다.

| 시험 | 확인 | 결함 재삽입 검증(고의로 깨뜨렸을 때 실패하는가) |
|---|---|---|
| 매트릭스 완전성 | 열거 파라미터 8개 × GW 7 = 56 셀이 전부 판정됐는가 | 한 행에서 셀 1개를 빼면 실패해야 한다 |
| `risk_score` 계산 | S×F 가 코드에서 계산되는가 | mock 이 `risk_score` 를 틀린 값으로 반환해도 결과가 옳아야 한다(모델 값 무시 확인) |
| 스키마 강제 | `converse` 에 `response_schema` 가 전달되는가 | `mock.calls[i]["response_schema"]` 가 None 이면 실패 |
| `content=None` 격하 | 그 행이 `review` 로 기록되고 예외가 나지 않는가 | 스키마 위반 응답 2회 주입 |
| 안전장치 환각 | 메타 `safeguards=[]` 인데 모델이 값을 채우면 어떻게 되는가 | 현 설계는 **통과시킨다** — FR-06 소관임을 시험 주석에 명시 |
| 프롬프트 외부화 | 프롬프트 문자열이 `.py` 에 없는가 | `generate.py` 에 5줄 이상 한글 프롬프트 리터럴이 있으면 실패 |

`pytest -m "not live"` 가 자격증명 없이 통과해야 한다. 실호출 테스트는 `@pytest.mark.live`.
