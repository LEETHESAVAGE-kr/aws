## 1. 문제 (심사위원이 처음 열었을 때)

1. **문서처럼 읽힌다.** 제목 → 단락 → ①②③ 소제목 → 표. 위에서 아래로 읽는 글이지, 뭔가를 "하는" 화면이 아니다. 누를 것이 드롭다운 하나뿐이고 그것도 이미 값이 채워져 있어 아무 것도 안 눌러도 된다.
2. **핵심 차별점이 숨어 있다.** 자연어 문장으로 HAZOP 을 만드는 기능이 드롭다운 4번째 옵션 "직접 입력 (빠른 실호출)" 뒤에 있다. 이름도 기능이 아니라 구현("실호출")을 말한다.
3. **맥락이 없다.** HAZOP 이 무엇인지, 현장에서 어떤 절차로 며칠씩 하는 일인지, 이 앱이 그 중 어디를 대신하는지가 화면에 없다. README §1 에만 있다. 심사위원은 README 를 안 읽는다.
4. **무엇이 실제 생성이고 무엇이 재생인지** 출처 줄 한 줄로만 구분된다 — 정직하지만 첫 화면에서 알아채기 어렵다.

### 4-2. HAZOP 60초 — 3열 카드 (`st.columns(3)`, 각 `st.container(border=True)`)

**① HAZOP 이 뭔가**
위험과 운전 분석(Hazard and Operability Study). 공정을 노드(배관·설비 구간)로 나누고, 각 노드의 파라미터(유량·압력·온도·조성…)에 가이드워드(No·More·Less·Reverse·Part of·As well as·Other than)를 하나씩 붙여 "설계 의도에서 벗어나는 경우(이탈)"를 빠짐없이 찾는 정성 위험성평가입니다. 국내에서는 공정안전보고서(PSM) 위험성평가의 표준 기법이고, KOSHA GUIDE P-82 가 절차를 정합니다.

**② 왜 무거운가 — 현장 절차**
1. P&ID 를 놓고 노드를 나눈다.
2. 리더·서기·공정·계장·운전·안전 담당이 한 방에 모인다.
3. 노드마다 파라미터×가이드워드 셀을 하나씩 짚으며 이탈·원인·결과를 토론한다.
4. 기존 안전장치를 확인하고 심각도(S)×빈도(F)로 위험도를 매긴다.
5. 권고사항을 정하고 워크시트·LOPA 로 문서화한다.
노드 하나에 회의 수 시간, 공장 하나에 노드 수십~수백 개. 매트릭스 셀을 빠뜨리지 않는 것 자체가 일입니다.

**③ 이 앱이 대신하는 것 / 사람이 하는 것**
대신하는 것: 파라미터 도출(3) → 가이드워드 전 셀 판정(3) → 원인·결과·안전장치·S×F·권고 초안(4) → 워크시트·LOPA 초안(5). 판정 셀은 100% 채우고, 근거 없는 규격 번호·수치는 verifier 가 🔴 로 표시합니다.
사람이 하는 것: 노드 정의(1), 초안 검토·수정, 최종 승인. **초안은 회의를 없애지 않고 회의 시작점을 올립니다.**
