## 0. 한 줄 판정

**지금 앱에는 "무엇을 지어내지 말라"는 금지 몇 줄만 있고, "어디까지 추론해도 되는가"를 정한 기준이 없다.**
그래서 모르는 정보는 조용히 빠지거나(열거 프롬프트는 "부족하다고 적지도 마라"), 일반론으로 메워진다. 사람은 어느 쪽인지 구분할 수 없다.
고칠 방향은 다섯 가지다.
① 정보를 4단계로 나눈다: 주어짐 · 근거 있음 · 일반 추론 · 미상.
② 노드 유형별로 "추론 허용 / 금지" 표를 만든다.
③ 미상인 정보를 쓰지 않고는 판단할 수 없는 셀은 **"정보 부족"으로 보류**하고, 무엇이 없어서 보류했는지 적는다. 피드백 "차라리 덜하는 것이 낫다"를 그대로 따른다.
④ 생성 전에 입력 충분성을 점검해 빠진 정보를 사용자에게 먼저 보여 준다.
⑤ 검증기가 입력에 없는 설비·계장·설정값을 찾아 표시한다.

Kiro API 는 **형식이 아직 확인되지 않았다**(§6 Q-K1). Anthropic 형식이면 코드 변경 0, 환경변수만 바꾸면 된다(10/8 F-01 배선 완료). 다른 형식이면 어댑터를 새로 하나 만든다.

## 3. 기능 요구사항

### Z-1 정보 4단계 (판단 기준) · P0

| 단계 | 표시 | 정의 | 예 | 허용 |
|---|---|---|---|---|
| **G 주어짐** | 입력 | 사용자 입력·노드 메타에 적힌 것 | "안전밸브", "90 MPa", "압축기" | 그대로 쓴다 |
| **S 근거 있음** | 인용 | 코퍼스(법령·고시·MSDS) 원문에 있는 것 | 암모니아 폭발범위 15~33.6 %(MSDS 9항), 안전밸브 설치 의무(기준규칙 제261조) | 인용을 붙일 때만 쓴다(Y-3 인용 계약) |
| **I 일반 추론** | 추론 | 주어진 설비·물질에서 물리적으로 따라 나오는 **일반** 고장 모드·결과 | 펌프 → 메커니컬 실 누설, 수소 → 넓은 폭발범위로 인한 점화 위험 | 쓸 수 있다. 다만 **수치·규격·특정 설비명 없이**, 행 신뢰도는 🟡 |
| **U 미상** | 확인 필요 | 입력에도 근거에도 없고, 일반론으로는 정할 수 없는 **사업장 고유 사실** | 인터록 설정값, 계장 태그, 안전밸브 유무(입력에 없을 때), 운전 절차, 설비 용량·재질 등급 | **추론 금지.** 문장에 사실처럼 쓰지 않는다. 판단에 꼭 필요하면 셀을 보류(Z-3)하고 `missing[]` 에 적는다 |

핵심 규칙: **"없음"과 "모름"을 구분한다.** 입력에 안전장치가 비어 있으면 "안전장치가 없다"(G)가 아니라 "안전장치를 모른다"(U)로 본다.
단, 사용자가 "안전장치 없음"이라고 명시하면 G 로 본다. 이를 위해 입력 스키마에 `safeguards_known: bool` 을 추가한다. 기본값은 false = 모름이고, 파서는 입력에 "없음"이 명시된 경우에만 true 로 바꾼다.

### Z-2 노드 유형별 추론 경계표 · P0

`data/kb/inference_policy.json` — 노드 유형은 설비 이름 키워드로 분류한다. 여러 유형에 걸리면 모두 적용한다.

| 노드 유형 | I 로 추론 허용 | U 라서 추론 금지 → 없으면 `missing` | 꼭 필요한 입력(Z-4 점검) |
|---|---|---|---|
| 저장탱크·용기 | 넘침·과압·진공 붕괴·부식 누설 같은 일반 모드 | 용량, 설계압력, 액위 계측·경보의 유무와 설정값, 방유제 유무 | 물질, 상, 운전압력(또는 상압 여부) |
| 펌프·압축기 | 실 누설, 체절 운전, 역회전, 과열 | 최소유량 보호 유무, 트립 설정값, 예비기 유무 | 토출 대상(어디로 보내는지) |
| 배관·호스·로딩암 | 파손·누설, 수격, 역류, 정전기 | 재질 등급, 체크밸브 유무, 브레이크어웨이·ERC 유무 | 양 끝 설비(어디서 어디로) |
| 열교환기·기화기 | 튜브 누설로 인한 혼입, 결빙, 과열 | 열매체 종류, 온도 제어 방식 | 열원·냉원 |
| 반응기 | 폭주 반응 같은 일반 모드 | 반응열, 냉각 용량, 원료 비율 | 반응 물질 |
| 운전 절차(충전·하역·절체) | 순서 착오, 조기·지연 조작 | 절차서 내용, 작업자 수, 확인 단계 | 절차 단계 목록 |
| 공통 | 물질 고유 위험(근거 있으면 S, 없으면 일반론만) | **입력에 없는 안전장치의 존재·작동 여부**, 수치 일체(입력·인용에 없는 것) | — |

- 이 표는 **초안**이다. 행과 열은 발표 전 사용자·지도 의견으로 고친다(Q-Z1).
- 표의 문구는 프롬프트에 그대로 들어간다(코드에 하드코딩하지 않는다, R-07).

### Z-3 셀 보류("정보 부족") · P0 — "차라리 덜하는 것이 낫다"

1. 판정 스키마의 셀 상태를 `applicable` / `not_applicable` / **`insufficient`** 셋으로 늘린다. `insufficient` 셀은 `missing: [U 항목]`(1~3개)과 `deviation` 초안을 가질 수 있지만 **S·F·원인 상세를 쓰지 않는다**.
2. 판정 규칙(프롬프트): "이 셀의 원인이나 S·F 가 표의 U 항목에 달려 있으면 `insufficient`. G·S·I 만으로 판단할 수 있으면 판정한다."
3. **F 와 안전장치**: `safeguards_known=false` 이면 F 를 "현재 안전조치 미상"으로 표시한다. 대안은 두 가지다(Q-Z2): (a) F 는 매기되 '안전조치 미반영' 배지를 붙인다 (b) F 를 비우고 S 만 매긴다.
4. 레코드 스키마에 `status`·`missing` 을 추가한다. 보류 행은 워크시트에 남기되 위험도는 비우고, Excel 에 '확인 필요' 시트를 붙인다(No · 이탈 초안 · 필요한 정보).
5. 매트릭스 누락 점검(판정 셀 n/n)에서는 보류 셀도 "판정함"으로 센다. 건너뛰기가 아니라 판단의 결과이기 때문이다.

### Z-4 입력 충분성 점검 · P1

1. 파싱 직후 노드 유형별 필수 정보(Z-2 마지막 열)를 대조해 "빠진 정보 n개"를 표시한다. 버튼은 [그대로 생성] [보완하고 생성] 두 개다.
2. 그대로 생성하면 빠진 정보가 U 로 들어가 보류 셀이 늘어난다. 화면에 이 결과를 미리 알린다.
3. 질문은 점검표에서 기계적으로 만든다. 모델이 질문을 지어내지 않는다.

### Z-5 검증기 `unsupported_entity` · P1

- 사전(`inference_policy.json` 의 `entity_terms`): 인터록, ESD, SIS, 트립, 설정값, 경보, 체크밸브, 과류차단, 브레이크어웨이 등.
- 원인·결과에 사전 단어가 나오는데 노드 메타(설비·안전장치)에도 인용에도 없으면 플래그를 단다 → 🔴.
- **권고는 예외**: "~ 설치 검토", "~ 유무 확인" 같은 제안 표현은 허용한다. 없는 것을 있다고 쓴 것이 아니기 때문이다.

### Z-6 화면·내보내기

- 행마다 '판단 근거' 열을 둔다: G/S/I/U 중 쓴 단계(예: "주어짐 + 일반 추론"). 보류 행은 '⚪ 정보 부족 — 안전밸브 유무 미상'으로 표시한다.
- 요약 줄 예시: "판정 84셀 = 해당 41 · 해당 없음 30 · **정보 부족 13**(보류)".
- 'HAZOP 이 처음이라면' 안내 탭에 "AI 가 추론하지 않는 것" 표를 추가한다(Z-2 공통 행).

## 4. Kiro API 연동 (K)

### 지금 상태(코드 사실)

- `core/llm` 은 Anthropic SDK(`AnthropicClient`)와 Bedrock(`BedrockClient`, 미검증 — 대회 계정 권한 없음, G0 종결)을 지원한다.
- 10/8 F-01: `ANTHROPIC_BASE_URL` + `ANTHROPIC_AUTH_TOKEN`(Bearer) 환경변수만으로 게이트웨이 경유가 된다. `service.SECRET_KEYS` 에 포함돼 있고, 출처 줄에 "대회 제공 API 경유" 표시가 나온다. 시험 `tests/test_gateway.py`(가짜 게이트웨이)로 확인했다.
- 모델 ID 는 `config/models.yaml` 에만 있다(추측 금지).

## 5. 비목표 · 리스크

- 비목표: 모델 자기평가(로그확률)로 U 를 판별하지 않는다. 규칙과 표로만 판별한다. 점검 결과를 사용자 입력 없이 자동으로 "보완"하지 않는다(자율성 제한의 취지).
- **R1 recall 하락**: 보류가 늘면 골드 대비 recall 이 내려갈 수 있다. 피드백이 받아들인 대가다("덜하는 것이 낫다"). 내려간 값을 그대로 공개하고, "정보 부족 셀의 골드 일치율"을 따로 잰다(보류한 셀이 실제로 골드에 있었는지).
- **R2 보류 남발**: 모델이 판정하기 어려우면 전부 보류할 수 있다. 사전 등록 상한을 둔다: 노드당 보류율이 40%를 넘으면 프롬프트를 조정한다.
- **R3 일정**: 발표 10/19. Z-1~Z-3(P0)과 K 는 10/14 동결, Z-4~Z-6 은 10/16. 못 맞추면 P1 은 접는다.
- **R4 포스터(10/12 제출)**: 이 기능은 포스터에 넣지 않는다. 발표에서 "본선 피드백 반영"으로 말한다.

## 7. Kiro spec 반영 (사용자 몫)

- 신규 spec `inference-boundary`: Z-1~Z-6. 태스크 ≤ 6.
