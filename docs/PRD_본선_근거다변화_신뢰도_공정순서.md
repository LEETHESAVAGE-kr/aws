# PRD — 근거 다변화(RAG) · 신뢰도 다단계 · No 공정 순서 (본선, 새 창 진입점)

작성 2026-10-09 · 브랜치 `finals` · 상위 문서 `PRD.md`(FR-04′·FR-05·FR-06), `docs/PRD_본선_전체가이드워드_보기.md`
근거: 사용자 피드백(10/9, 원문 §1)

---

## 0. 한 줄 판정

**세 지적 모두 코드에서 사실로 확인된다.**
① 신뢰도는 생성 단계에서 **`inferred` 하나뿐**이고 검증기가 `review` 로 내리기만 한다 — `grounded` 를 주는 코드가 없다.
② S·F 등급 기준은 **NH3 선박 간(STS) 벙커링 평가기준 하나**가 프롬프트·Excel 에 고정돼 있고, 근거 인용(`evidence[]`)은 스키마가 **빈 배열만 허용**한다.
③ No 는 **가이드워드 순서 우선**(No 전부 → More 전부 → …)이라 공정 흐름 순서가 아니다.
고치는 방향: 공식 기준 문서를 여러 개 모아 검색(RAG)해 행마다 근거를 붙이고, 근거의 수·일치 여부로 신뢰도를 여러 단계로 매기고, No 는 공정 순서 키로 다시 매긴다.
**일정 제약**: 최종 발표 10/19 · 부스 10/20. RAG·신뢰도는 생성 경로를 바꾸므로 실측(정확도·비용·지연) 재측정까지 포함해 **10/16 동결**을 목표로 하고, 못 맞추면 P1 부분은 접는다(§8).

## 1. 피드백 원문과 판단

> 신뢰도가 하나야 그리고 근거가 sts 벙커링만 있는게 마음에 안들어 공식 기준으로 딥러닝이라 rag 등으로 단일 기준을 벗어나서 다변수 근거가 되었음 좋겠음
> 또한 no가 공정순서대로 나왔으면 좋겠는데 지금도 그런지 확인하고 수정할거야

| 피드백 | 판단 | 근거(코드 사실) |
|---|---|---|
| 신뢰도가 하나다 | **수용.** 근거 기반 다단계로 | 생성 응답 스키마가 `confidence` enum `["inferred"]` 하나(`core/agent/generate.py:129`), 레코드 조립도 `confidence="inferred"` 고정(`generate.py:518`). 검증기는 `review` 격하만 하고 "`grounded` 는 부여하지 않는다"(`core/agent/verify.py:5`) |
| 근거가 STS 벙커링 하나다 | **수용.** 공식 기준 여러 개 + 공정별 적용 | 판정 프롬프트에 `data/gold/rating_scale.json`(NH3 벙커링 평가기준)만 주입(`generate.py:404`). Excel '평가기준' 시트도 같은 파일(`core/export/xlsx.py:61`). 산출물 스키마 `evidence` 는 `maxItems: 0`(`schemas/deviation.schema.json:47`) — 근거를 붙일 자리가 없다. `data/kb/` 에는 `hazop_param_examples.json` 하나뿐, 예선 PRD 의 FR-04′(KOSHA 발췌 로컬 인용)는 **미착수** |
| RAG(딥러닝)로 다변수 근거 | **수용 — 방식은 Q2 로 결정.** Bedrock KB 는 대회 계정 권한이 없고(G0 종결), Anthropic API 엔 임베딩이 없다. 로컬 임베딩 / 외부 임베딩 API / 키워드 검색(BM25) 중 고른다 | `PRD.md` §3.2·FR-04′, 메모리 G0 종결 |
| No 가 공정 순서인가 | **아니다(확인).** 노드 안에서는 가이드워드 축 순서 → 그 안에서 파라미터 열거 순서 | `_build_records` 가 가이드워드 묶음 순서대로 행을 쌓고 `id` 를 매긴다(`generate.py:479-519`), Excel `No` 는 입력 순서(`core/export/rows.py` `normalize_rows`). 노드 간 순서는 '공정 전체 보기'(지시문 X-3)에서만 노드 순서 |

### No 순서 — 현재 실제 출력 예 (10/9 수소충전소 실호출, 76행)

`1 No(유량) · 2 No(압력) · 3 No(준위) · 4 No(기동정지) … → More(유량) · More(압력) …` — 같은 파라미터(예: 압력)의 No·More·Less 가 수십 행 떨어져 있다.
골드셋(전문가 작성 34건)은 **노드 순서(N1→N4)** 를 따르고, 노드 안에서는 대체로 파라미터별로 모여 있다(엄격한 규칙은 아님).

## 3. 기능 요구사항

### Y-1 No 공정 순서 · P0 (모델 호출 변경 없음)

1. 정렬 키 하나(`process_order_key`)를 정의하고 **표·내보내기·검토·검증 결과가 모두 이 순서**를 쓰게 한다. 레코드 `id` 는 정렬 뒤 다시 매긴다(새 생성 결과). 재생 파일은 고치지 않고 불러올 때 정렬한다.
2. 파라미터 순서: 열거 결과 순서를 그대로 쓰되, 열거 프롬프트에 "**물질이 흐르는 순서(받는 곳 → 내보내는 곳)와 표준 공정변수(유량·압력·온도·준위·조성) 먼저**"를 요구한다 — 프롬프트 변경이므로 Y-G5 재측정 대상.
3. 가이드워드 축 순서는 지금과 같다(No·More·Less·Reverse·Other than·Part of·As well as, 절차형 3종).
4. 보기 전환(지시문 X)의 '워크시트 순서' = 공정 순서. '가이드워드별'·'파라미터별'은 그대로.
5. (Q1-B 를 고르면) 셀에 `equipment`(노드 메타의 설비 목록 중 하나) 필드를 추가하고 설비 흐름 순서를 정렬 1순위로 — 스키마·프롬프트 변경.

### Y-2 평가기준 다변화 · P0

1. `data/kb/criteria/` 에 기준 파일을 **출처와 함께** 둔다(형식은 지금 `rating_scale.json` 과 같게: severity·frequency 1~5 정의 + risk_bands + `source`·`license`·`retrieved_at`).
   - `nh3_sts_bunkering.json` — 지금 파일(골드셋 평가기준, 본인 저작물). **골드셋 노드 전용.**
   - 공식 기준 후보(출처·라이선스를 **원문으로 확인한 뒤에만** 추가 — 기억으로 등급 정의를 쓰지 않는다): 고용노동부 「사업장 위험성평가에 관한 지침」(고시)의 빈도·강도 예시, KOSHA GUIDE P-82(연속공정 HAZOP 기술지침)의 위험도 산정 예, KOSHA 위험성평가 관련 지침. 5단계가 아니면 **5단계로 바꾸지 말고** 원래 단계 그대로 쓰고 화면에 단계 수를 적는다.
2. 기준 선택 규칙: 골드셋 노드 → NH3 기준, 그 밖(직접 입력·예시·외부 대조) → 공식 기준 기본값. 사용자가 화면에서 바꿀 수 있게 할지는 Q3.
3. 판정 프롬프트의 `{rating_scale}` 자리에 고른 기준을 넣고, 결과 메타에 `criteria_id` 를 남긴다. 화면의 '평가기준 참고용' 배지(지시문 M-03)는 "이 결과는 〈기준 이름〉 기준으로 매겼습니다"로 바뀐다.
4. Excel '평가기준' 시트 = 실제 쓴 기준. 시험이 대조한다(`core/export/report.py:22` 의 문자열 일치 시험 갱신).

### Y-3 근거 인용(RAG) · P1

1. **코퍼스**(`data/kb/corpus/`): 공식 문서 발췌를 문단 단위 JSON 으로 — `{source_id, doc_title, issuer, year, locator(조·항·쪽), text, license}`. 후보: KOSHA GUIDE(HAZOP·위험성평가·해당 설비 지침), 고용노동부 고시, 물질 정보(MSDS 공공 DB), 공개 사고사례 요약. **수집 전 이용 조건 확인**, 확인 못 한 문서는 넣지 않는다. 고객사 자료 금지(불변 규칙 1).
2. **검색**: 셀(노드 메타 + 가이드워드 + 파라미터 + 이탈 초안)을 질의로 상위 k(기본 3)개. 방식은 Q2. 검색 결과는 판정 호출의 사용자 메시지에 "참고 발췌(인용은 이 안에서만)"로 넣는다.
3. **인용 계약**: 모델은 `evidence[]` 에 발췌의 `source_id` 와 원문 **부분 문자열**만 낸다. 코드가 (a) `source_id` 가 이번 검색 결과에 있는지 (b) `quote` 가 그 발췌 원문의 부분 문자열인지 검사하고, 어긋나면 그 인용을 **지우고 플래그**(FR-06 규칙 확장). 검사기는 결함 재삽입 시험으로 고정.
4. 화면: 검토 표에 '근거' 열(출처 수 · 첫 출처 이름), 행을 고르면 발췌 원문. Excel '근거' 시트(이미 있음 — `xlsx.py` SHEET_ORDER)에 실제 인용을 채운다.
5. 비용·지연: 판정 호출 입력이 발췌만큼 늘어난다(셀 수 × k). 측정 전 상한을 정한다 — 노드당 비용 +30% 넘으면 k 를 줄인다(사전 등록).

### Y-4 신뢰도 다단계 · P1

| 단계 | 표시 | 조건(전부 코드 판정 — 모델 자기평가 아님) |
|---|---|---|
| 근거 다수 | 🟢 | 서로 다른 출처(`issuer` 기준) 2곳 이상 인용, 인용 검사 통과, 검증기 플래그 0 |
| 근거 1건 | 🔵 | 인용 1곳, 검사 통과, 플래그 0 |
| 추론 | 🟡 | 인용 없음, 플래그 0 |
| 검토 필요 | 🔴 | 검증기 플래그(근거 없는 규격·수치·가짜 인용) 또는 스키마 2회 실패 |

- 스키마 `confidence` enum 을 4값으로, 내보내기 사유 표(`CONFIDENCE_REASONS`)·화면 배지·'HAZOP 이 처음이라면' 설명 탭을 같이 고친다.
- **주의(정직 보고)**: 근거가 붙었다고 내용이 맞는 것은 아니다 — "근거 다수"는 "공식 문서가 같은 위험을 다룬다"는 뜻이지 정답 보증이 아니라고 화면에 적는다. 정확도(recall)와 신뢰도 단계의 관계는 Y-G5 에서 따로 잰다(🟢 행이 실제로 골드와 더 많이 맞는가).

## 4. 비목표

- Bedrock Knowledge Base(대회 계정 권한 없음 — G0 종결). 대회 키 전환 뒤 가능하면 백로그.
